TD Engine

An open-source game engine built on a C / C++ core with a JavaScript / TypeScript bridge for the web. The same code runs on Windows desktop and in any modern browser — ECS, networking, voxel, UI toolkit, scripting VM, audio, all in one.

One codebase. Two runtimes. Zero compromise.

// Desktop-class performance, web-class reach

// THE PROBLEM

Most web game engines are JavaScript-first — they pay a JIT tax on every frame, struggle with typed-array ergonomics, and can't reuse desktop code paths. Most desktop engines (Unity, Unreal, Godot) treat the web as an afterthought export target — multi-megabyte loaders, broken audio, no real multiplayer story.

TD Engine is built around a different bet: write portable C++17, compile it once with Emscripten, ship a single ~1 MB .wasm file. The browser provides the platform layer (canvas, audio device, input, WebSocket). The engine provides everything else.

// THE CODE

// Same C++ runs on Windows desktop AND in the browser. auto& ecs = world.getECS(); auto e = ecs.createEntity(); ecs.setPosition(e, {100, 200}); ecs.setSprite(e, "ship.png"); ecs.setCollider(e, {32, 32}); // JS bridge calls into the WASM module via cwrap: const e = TDEngine.ecs.create(); TDEngine.ecs.setPosition(e, 100, 200); TDEngine.ecs.setSprite(e, "ship.png"); // Multiplayer is one line: TDNet.Peer.join("arena-1");

What's in the box

// 16 production-ready subsystems, all header-only or single-.cpp

E

Archetype ECS

Contiguous arrays per archetype. 10,000 entities boot in <5ms. Component add/remove via swap-back pop. Validated by 6 test suites.

N

Networking

Reliable UDP transport + RPC system. Client prediction + server reconciliation. Web transport via WebSocket + BroadcastChannel (P2P cross-tab).

  • TDNet.Socket — WebSocket transport
  • TDNet.Peer — BroadcastChannel P2P
  • TDNet.RPC — async call/result
V

Voxel world

Greedy mesher (5–10x fewer triangles). 4-octave simplex worldgen. Sunlight + BFS block light. Frustum-culled chunk streaming.

U

UI toolkit

13 widgets (Container, Label, Button, Slider, TextInput, ScrollView, ListView, Dropdown, Modal, Tooltip, Canvas). Real flexbox layout. Virtualized 10K-item lists at <1ms.

S

Scripting VM

Custom Lua-like bytecode interpreter (3,075 LOC). Lexer → parser → compiler → stack VM. Hot-reload at runtime. Visual script graph compiler emits tdscript source.

R

Renderer

WebGL2 / OpenGL 3.3 backend (same shaders, different GLSL version header). Sprite batcher, framebuffer effects, camera, texture atlas. ~5,000 sprites per frame at 60 FPS on a laptop.

P

Physics

AABB collision, swept capsule controller, sliding, slope limit, step handling, ground detection. Rigid body dynamics. Validated by 4 test suites.

A

Audio

WAV decoder, mixer, spatial 3D audio with HRTF-lite panning, Schroeder reverb, Doppler. Web Audio backend in the browser, waveOut on Windows.

I

i18n + mobile

Locale fallback, plural forms, RTL detection (Arabic flips the HUD). Multi-touch + gestures, 6-DoF XR controllers, Standard Gamepad mapping.

The stack

// Four languages, one engine. Each layer has a clear job.

C

Portable core

The lowest layer — math, allocator hooks, and the plugin ABI. Pure C89 so it can be called from anywhere with no C++ runtime.

src/core/* · src/plugin/plugin_abi.h
C++

Engine subsystems

16 subsystems (ECS, renderer, physics, audio, networking, voxel, UI, scripting VM). C++17, no STL bloat, compiles to both native and WASM.

src/ecs · src/renderer · src/net · src/voxel · ...
JS

Web bridge

Thin Emscripten cwrap bindings + pure-JS modules for things browsers do best (WebSocket, BroadcastChannel, IndexedDB, Web Audio).

wasm/js_bridge.js · web/td_api.js · web/net_websocket.js
TS

Game code

You write your game in TypeScript (or plain JS). The engine ships .d.ts typings so your editor knows every API. No editor app — just VSCode.

your-game/ · tde.d.ts (planned)

The workflow

// Your game lives in your folder. The engine lives in node_modules / a submodule. Nothing else.

// NO BUNDLED EDITOR

TD Engine is not an editor application. There is no td-editor.exe in the default build. You write your game in VSCode (or any editor you like), in a folder you own. The engine is a dependency you pull in.

This keeps your game code decoupled from the engine, lets you use any build tool you want (Vite, esbuild, plain tsc), and means the engine never has to ship a UI app that competes with the tools you already know.

For shipping outside the browser, the planned EXE bundler (roadmap) will wrap your JS game + the engine WASM into a single Windows .exe so you can sell it on Steam / itch.io.

my-game/ ├── package.json ├── tsconfig.json ├── src/ │  ├── player.ts │  └── main.ts ├── assets/ │  └── ship.png └── node_modules/     └── td-engine/         ├── td-engine.wasm         ├── js_bridge.js         └── tde.d.ts # Dev: open in VSCode, run `vite`, # iterate. Self-host on your own VPN

// No vendor lock-in. The engine is just static files.

// DEPLOY ANYWHERE

The entire engine is a ~1 MB .wasm file plus ~200 KB of JS glue. Drop it on GitHub Pages, your own VPS, a CDN, or an intranet — any static host works.

Add ?server=https://your-vpn.example.com/td/ to the page URL and the engine will load all assets (wasm, js, sprites, audio) from your server instead of the default origin. No recompile, no config file, no environment variables.

For multiplayer, run a 50-line Node.js WebSocket server (the wire format matches the C++ RpcServer). Point TDNet.Socket at it and you have internet multiplayer.
