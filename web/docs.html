TD Engine Documentation

TD Engine is a multi-language game engine: a C / C++17 core that compiles to WebAssembly, with a JavaScript / TypeScript bridge for the web. The same source runs on Windows desktop and in any modern browser. This page covers the JavaScript API (the layer you write game code against when targeting the web), plus self-hosting and multiplayer guides.

What is TD Engine?

TD Engine is built on a simple bet: write portable C / C++ once, compile it to WebAssembly, ship a single ~1 MB .wasm file. The browser provides the platform layer (canvas, audio device, input events, WebSocket). The engine provides everything else — ECS, renderer, physics, audio, networking, scripting, UI toolkit, voxel world, i18n.

On Windows desktop, the same C++ source links against Win32 + OpenGL + waveOut. On the web, it links against Emscripten + WebGL2 + Web Audio. There is no "web port" — it's the same code, two platform backends.

The stack is four languages, each with a clear job:

  • C — the lowest layer: math, allocator hooks, the plugin ABI. Pure C89, callable from anywhere.
  • C++17 — the engine subsystems (ECS, renderer, physics, audio, net, voxel, UI, scripting VM). 26K LOC, no STL bloat.
  • JavaScript — the web bridge. Thin Emscripten cwrap bindings + pure-JS modules for things browsers do best (WebSocket, BroadcastChannel, IndexedDB, Web Audio).
  • TypeScript — what you write your game in. The engine ships .d.ts typings (planned) so your editor knows every API. No editor app — just VSCode.

The JavaScript layer (what you write game code against) is a thin wrapper around the C API exposed by the WASM module. It uses Emscripten's ccall / cwrap to call into C++ functions like _td_create_entity, _td_entity_set_position, etc. The wrapper lives in web/td_api.js and exposes the TDEngine.* namespace.

No bundled editor.   TD Engine is not an editor application — there is no td-editor.exe in the default build. You write your game in VSCode (or any editor you like) in a folder you own. The engine is a dependency you pull in. This keeps your game code decoupled from the engine and lets you use any build tool (Vite, esbuild, plain tsc). For shipping outside the browser, the planned EXE bundler (roadmap) wraps your JS game + the engine WASM into a single Windows .exe for Steam / itch.io.

Quickstart (web)

The fastest way to get started is to clone the repo, drop the web/ folder into your project, and boot the engine on a canvas. Here's the minimal pattern:

New: 3D Sandbox Demo   — a playable 3D physics playground that exercises every engine subsystem (physics, ECS, input, audio, i18n, persistence, beat, shaders, networking hooks) in a single scene. Play the demo →   or browse the source at examples/3d-showcase/. The demo runs without the compiled WASM — a pure-JS fallback physics engine kicks in so you can play immediately. When you run td serve, the same demo uses the real C++ physics backend automatically. 
// 1. Load the engine scripts in your HTML <head>
<script src="js_bridge.js?v=24"></script>
<script src="td_api.js?v=24"></script>

// 2. Boot the engine on a canvas
await TDBridge.init('game-canvas');

// 3. Use the modular API
const player = TDEngine.ecs.create();
TDEngine.ecs.setPosition(player, 100, 200);
TDEngine.ecs.setSprite(player, "ship.png");
TDEngine.ecs.setCollider(player, 32, 32);

// 4. Game loop — engine handles rAF + WASM render
function update() {
  if (TDEngine.input.isKeyDown('KeyA')) {
    const [x, y] = TDEngine.ecs.getPosition(player);
    TDEngine.ecs.setPosition(player, x - 4, y);
  }
  requestAnimationFrame(update);
}
update();
What just happened:   TDBridge.init() downloads td-engine.wasm, instantiates it, creates a WebGL2 context on your canvas, and registers the engine's mainLoop with requestAnimationFrame. Once await TDBridge.init() resolves, you can call any TDEngine.* API. The engine renders every frame automatically — you only need to update entity state.

Quickstart (desktop)

On Windows, the engine builds with CMake + MSVC (or Ninja). The same source also builds on Linux/macOS with GCC/Clang, but the platform layer (src/platform/win32_window.cpp) is Windows-only. 

# Clone and configure
$ git clone https://github.com/hacvilke/td
$ cd td
$ cmake -B build -S .

# Build everything (engine + examples + tests, editor OFF by default)
$ cmake --build build --parallel

# Run an example
$ ./build/bin/pong.exe
$ ./build/bin/platformer.exe

# Run unit tests
$ cd build && ctest --output-on-failure

# (Optional) build the editor explicitly if you want it
$ cmake -B build -S . -DTD_BUILD_EDITOR=ON && cmake --build build
Why no editor by default?   The engine's direction is "you write your game in VSCode, the engine is a dependency." Shipping an editor EXE competes with tools you already know and adds build weight. The editor source is still in editor/ for anyone who wants it — just flip -DTD_BUILD_EDITOR=ON. The planned EXE bundler (roadmap) is a separate tool that wraps your finished JS game into a sellable Windows .exe.

Architecture

The engine has four language layers, each one fully open-source:

  1. C core (src/core/, src/plugin/plugin_abi.h) — math, allocator hooks, the plugin ABI. Pure C89, callable from anywhere with no C++ runtime.
  2. C++17 subsystems (src/) — 26K LOC across 16 subsystems. No external dependencies. This is where the real work happens.
  3. WASM platform (wasm/emscripten_main.cpp) — exposes the C++ API as extern "C" functions that Emscripten exports to JavaScript.
  4. JS bridge + modular API (web/js_bridge.js + web/td_api.js) — wraps the C API in a clean, Godot-like namespace. You write your game in TypeScript on top of this.

The web runtime is split into focused modules, each loaded as a separate <script> tag:

  • js_bridge.js — loads WASM, manages the GL context, pipes engine logs to the on-page console
  • td_api.js — the TDEngine.* namespace (lifecycle, ecs, input, beat, script, i18n, audio, touch, gamepad)
  • net_websocket.js — TDNet.Socket + TDNet.RPC + TDNet.ServerConfig
  • net_peer.js — TDNet.Peer (BroadcastChannel P2P)
  • server_router.js — lets users self-host the engine on their own VPN
  • deprecated_tracker.js — Godot-like deprecated API warning system
  • inspector.js — live ECS entity/component browser
  • profiler.js — frame-time graph + counters + heap meter
  • error_boundary.js — friendly crash card with stack trace
  • persistence.js — save/load with game-registered serializers

Lifecycle

The engine has a single boot entry point and a single shutdown hook. Everything else is event-driven. All lifecycle methods are on the TDEngine.lifecycle namespace (in web/td_api.js).

FunctionDescription
await TDEngine.lifecycle.init(canvasId)Async. Downloads .wasm, creates GL context, starts the render loop. Resolves when the engine is ready. Idempotent — calling twice is a no-op.
TDEngine.lifecycle.onReady(cb)Register a callback that fires once when the engine is ready. If already ready, fires synchronously.
TDEngine.lifecycle.shutdown()Tears down the engine: stops the render loop, frees WASM resources, calls td_shutdown.
TDEngine.lifecycle.getVersion()Returns the engine version string (e.g. "1.0.0").
TDEngine.lifecycle.isReady()Returns true once init() has resolved.
TDEngine.lifecycle.resize(w, h)Resize the engine's GL context + canvas. Call when the canvas element resizes.

Low-level bridge access is also available (for cases where the TDEngine.* wrapper doesn't expose what you need):

FunctionDescription
TDBridge.init(canvasId)Async. Low-level WASM boot. TDEngine.lifecycle.init calls this — prefer the wrapper.
TDBridge.onReady(cb)Low-level ready callback.
TDBridge.onLog(cb)Register a callback for engine log lines. cb({level, message}) where level is info|warn|error|deprecated.
TDBridge.resumeAudio()Resumes the Web Audio context (must be called from a user gesture, e.g. a click).
TDBridge.getVersion()Returns the engine version string.

ECS

The entity-component-system is the core of the engine. Entities are integer IDs. Components are attached via setter functions. The engine renders every active sprite-carrying entity each frame. 

// Create an entity (returns a numeric ID). Optional name for debugging.
const e = TDEngine.ecs.create("Player");

// Set components (all setters take the entity ID first).
TDEngine.ecs.setPosition(e, 100, 200);
TDEngine.ecs.setVelocity(e, 0, -50);          // pixels per second
TDEngine.ecs.setSprite(e, 64, 64, 1, 1, 1, 1);  // w, h, r, g, b, a (each 0..1)
TDEngine.ecs.setCollider(e, 32, 32);           // w, h in pixels

// Read back position (the only getter currently exposed).
const pos = TDEngine.ecs.getPosition(e);  // returns { x, y }

// Lifecycle.
TDEngine.ecs.isValid(e);                     // false after destroy()
TDEngine.ecs.destroy(e);
TDEngine.ecs.count();                          // active entity count
Known limitation:   The C++ ECS API currently exposes only a position getter. Velocity, sprite, and collider are write-only from JS. This is why the inspector shows entities + positions but not full component state — and why persistence uses game-registered serializers instead of auto-serializing the ECS. Exposing more getters is on the roadmap.

Input

Keyboard, mouse, touch, and gamepad are all unified under TDEngine.input. State is polled (not event-based) so you can read it any time inside your game loop.

Keyboard codes are Win32 VK codes (not KeyboardEvent.code strings). The TDEngine.input.Key table provides friendly constants (TDEngine.input.Key.A, .Space, .ArrowLeft, etc.) so you don't have to memorize the numbers.

FunctionDescription
input.isKeyDown(vk)VK code (use TDEngine.input.Key.A, .Space, .Left, etc.). Returns bool.
input.isMouseDown(button)button is 0 (left), 1 (middle), 2 (right). Returns bool.
input.getMousePos()Returns { x, y } in canvas pixels.
input.KeyVK code constants: .A...Z, .Num0...Num9, .F1...F12, .Left/Right/Up/Down, .Space, .Enter, .Escape, .Shift, .Control, .Alt.
input.MouseMouse button constants: .Left = 0, .Right = 1, .Middle = 2.
if (TDEngine.input.isKeyDown(TDEngine.input.Key.Space)) {
  jump();
}
const { x, y } = TDEngine.input.getMousePos();
if (TDEngine.input.isMouseDown(TDEngine.input.Mouse.Left)) {
  fireBullet(x, y);
}

Touch and gamepad are separate namespaces for clarity:

FunctionDescription
TDEngine.touch.count()Number of active touch points.
TDEngine.touch.x(i) / .y(i)Position of touch point i.
TDEngine.touch.pinchScale()Pinch-to-zoom scale factor relative to touch-start.
TDEngine.gamepad.buttonPressed(idx, btn)Standard Gamepad button state.
TDEngine.gamepad.axis(idx, axis)Returns the analog stick value, normalized to [-1, 1]. Axis 0 = X, 1 = Y.

Beat System

The beat system drives rhythm-game mechanics. It schedules callbacks on a fixed BPM grid and tracks combos for on-beat hits. Each entity can have its own beat tracker — multiple entities with different BPMs coexist on the same world. 

// Attach a beat tracker to an entity. 140 BPM, 150ms half-window (300ms total).
TDEngine.beat.start(songEntity, 140.0, 0.15);

// Beat callback receives (beatCount, beatTime) — beatTime is in seconds.
TDEngine.beat.setCallback((beatCount, beatTime) => {
  console.log("beat #" + beatCount + " at " + beatTime.toFixed(3) + "s");
  spawnNote(beatCount);
});

// In a keydown handler:
if (TDEngine.beat.isOnBeat(songEntity)) {
  const newCombo = TDEngine.beat.registerHit(songEntity, false);  // returns combo count
  score += 100 + newCombo * 10;                                          // game's scoring formula
}

// Change BPM mid-song (recomputes spb + bounds).
TDEngine.beat.setBpm(songEntity, 160.0);

// Stop tracking.
TDEngine.beat.stop(songEntity);

The full 13-method surface:

FunctionDescription
beat.start(entityId, bpm, windowHalfSec)Attach a BeatTrackerComponent with the given BPM and tolerance.
beat.stop(entityId)Detach the component.
beat.isOnBeat(entityId)Returns true if inside the on-beat window (two-half-window trick — see docs/RHYTHM_MECHANICS.md).
beat.getCount(entityId)Total beats elapsed since start().
beat.getNextBeatTime(entityId)Engine time (seconds) of the next beat tick.
beat.getLastBeatTime(entityId)Engine time (seconds) of the most recent beat tick.
beat.registerHit(entityId, strict)Record a player hit. Returns the new combo count (not a score delta). With strict=true, a hit outside the on-beat window resets combo and returns 0.
beat.getCombo(entityId)Current hit-combo count.
beat.getBestCombo(entityId)Best combo this session.
beat.resetCombo(entityId)Reset combo to 0. Returns the previous combo count.
beat.setCallback(cb)Register a JS callback invoked on every beat tick. Signature: function(beatCount, beatTime).
beat.setBpm(entityId, newBpm)Change BPM mid-song. Recomputes spb and the bounds.
beat.playSound(entityId, wavIndex)Play a one-shot metronome tick through the mixer.

Scripting VM (tdscript)

The engine ships with a custom Lua-like bytecode interpreter (~3,100 LOC of C++). Scripts are compiled at runtime from source strings and can call back into C++ functions. See src/scripting/tdscript/ for the lexer + parser + codegen + VM. 

const src = `
  fn spawn_burst(x, y) {
    emit particles at x, y with color = palette[current]
  }
  fn toggle_gravity() { gravity = !gravity }
`;

const handle = TDEngine.script.load(src, "effects");

// args may be a plain JS array OR a JSON-encoded string. The C side
// expects a JSON array string; the wrapper auto-stringifies for you.
const result = TDEngine.script.call(handle, "spawn_burst", [100, 200]);

TDEngine.script.unload(handle);
FunctionDescription
script.load(src, name?)Compile a tdscript source string. Returns a numeric handle.
script.call(handle, fnName, args?)Call a function inside the loaded script. args is a JS array or JSON string. Returns the function's return value as a string.
script.unload(handle)Free the script's VM state.

i18n

Load locale tables into the engine, then look up strings by key. Arabic flips to RTL automatically. load() accepts either a plain JS object (auto-stringified) or a JSON-encoded string (matches the C API directly). 

// Pass a plain object — the wrapper JSON-stringifies it for the C side.
TDEngine.i18n.load('en', { play: 'Play', quit: 'Quit' });
TDEngine.i18n.load('ar', { play: 'العب',  quit: 'اخرج' });
TDEngine.i18n.setLocale('ar');

const s = TDEngine.i18n.t('play');   // 'العب'
const rtl = TDEngine.i18n.isRtl();       // true

3D Physics

The TDEngine.physics namespace exposes a full 3D rigid body simulator (spheres, boxes, capsules, convex hulls) with sequential-impulse solver, Coulomb friction, restitution, sleeping, and constraints (distance, hinge). Backed by src/physics/physics_world_3d.{h,cpp}, exposed via the td_physics_* C bridge. 

// Create a world with gravity (here: -9.81 on Y).
TDEngine.physics.init(0, -9.81, 0);

// Static floor (mass=0, isStatic=true).
const floor = TDEngine.physics.addBody(0, 0, -5, 0, true);
TDEngine.physics.setBoxCollider(floor, 10, 1, 10);

// Dynamic ball.
const ball = TDEngine.physics.addBody(1, 0, 5, 0, false);
TDEngine.physics.setSphereCollider(ball, 0.5);
TDEngine.physics.setRestitution(ball, 0.8);

// Each frame: step the world + read back positions.
function gameLoop(dt) {
  TDEngine.physics.step(dt);
  const { x, y, z } = TDEngine.physics.getPosition(ball);
  const orient = TDEngine.physics.getOrientation(ball); // quaternion {x,y,z,w}
}

// Raycast: returns { bodyId, point, normal } or null.
const hit = TDEngine.physics.raycast(0,5,0, 0,-1,0, 100);

Networking

Two transports, same API shape:

  • TDNet.Socket — WebSocket transport for internet multiplayer. Requires a server (a 50-line Node.js script is enough; the wire format matches the C++ RpcServer).
  • TDNet.Peer — BroadcastChannel transport for cross-tab multiplayer. No server needed. Sub-millisecond latency. Works in all modern browsers.
// P2P — open this page in 2+ tabs
const peer = new TDNet.Peer.join('arena-1');

peer.onPeerJoin(p => console.log('joined:', p.id));
peer.onMessage((from, msg) => console.log(msg));
peer.onPeerLeave(p => console.log('left:', p.id));

peer.send({ kind: 'pos', x: 100, y: 200 });       // broadcast
peer.sendTo(peerId, { kind: 'shoot' });              // directed

const rtt = peer.rtt();  // milliseconds, measured via ping/pong
// Internet — point at your own WebSocket server
const sock = new TDNet.Socket.connect('wss://your.server/td');

sock.onMessage(msg => console.log(msg));
sock.send({ kind: 'hello' });

// RPC — async call/result, like JSON-RPC
const result = await sock.rpc('getLeaderboard', { game: 'pong' });

Persistence

Web games lose everything on F5. The persistence module fixes that with localStorage-backed save slots and game-registered serializers. You decide what to save — the engine won't auto-serialize the ECS (because most state isn't exposed via getters). 

// Register a serializer for your game state
TDPersistence.registerSerializer('player', {
  save: () => ({ x: playerX, y: playerY, hp: playerHP }),
  load: (data) => { playerX = data.x; playerY = data.y; playerHP = data.hp; }
});

// Save to a named slot
TDPersistence.save('checkpoint-1');

// Load it back later (or on next page load)
const result = TDPersistence.load('checkpoint-1');
if (result.ok) console.log('restored:', result.restored);

// Autosave every 30 seconds
const handle = TDPersistence.autosave('auto', 30000);
handle.stop();  // stop autosaving

// Export to a .json file (shareable)
const json = TDPersistence.exportJson('checkpoint-1');
TDPersistence.importJson(json);  // round-trip

Inspector

The inspector is a live ECS entity/component browser. It auto-refreshes at 4 Hz and shows every active entity, its ID, and its position. Useful for debugging "why isn't my sprite showing". Mount it in your own dev UI — there's no built-in editor top bar. 

// Programmatic API (for headless testing or custom UI)
const snap = TDInspector.snapshot();
console.log(snap.entityCount, snap.entities);

// Mount into your own container
const handle = TDInspector.mount(containerEl, { refreshMs: 250 });
handle.unmount();

Profiler

The profiler is a rolling frame-time graph you mount in your own dev UI. It draws 60 FPS and 30 FPS budget lines, named counters, vertical markers (for events like "scene load"), and a WASM/JS heap meter. 

const handle = TDProfiler.mount(containerEl, { refreshMs: 100 });

// In your game loop:
handle.frame(deltaMs);
handle.counter('drawCalls', drawCallCount);
handle.increment('spawns');
handle.mark('scene-load');

handle.unmount();

Game Kit — TDAssets (asset pipeline)

web/game_kit.js exposes four namespaces aimed at web-development workflows: TDAssets (this section), TDCDN, TDRest, TDServer. All are pure-JS IIFEs with zero external dependencies; loaded additively in web/index.html. See docs/GAME_KIT.md for the full reference.

TDAssets wraps fetch() with retry, caching, and the decode/upload helpers you need to turn a URL into an in-engine Texture or an AudioBuffer ready for Web Audio. Works with any CORS-enabled URL: your own CDN, GitHub raw, Openverse, Freesound (via the asset proxy), Unsplash (via the asset proxy), DiceBear, PokéAPI, etc. 

// One-shot: fetch URL → decode → upload → return texture ID.
const texId = await TDAssets.loadTexture('https://cdn.example.com/ship.png');

// Fetch + decode audio into an AudioBuffer.
const audioBuf = await TDAssets.loadAudio('https://cdn.example.com/jump.wav');

// Low-level: fetch bytes / text / parsed JSON.
const bytes = await TDAssets.fetchBytes(url);
const text  = await TDAssets.fetchText(url);
const cfg   = await TDAssets.fetchJson(url);  // parsed

// Cache management (shared with TDRest).
TDAssets.cacheClear();
TDAssets.cacheSize();   // total bytes tracked
TDAssets.cacheCount();  // entry count

Game Kit — TDCDN (multi-origin routing)

Define a list of CDN prefixes for your game's assets; the engine resolves each logical path against them in weight order until one returns 200. Same API in dev (local files) and prod (CDN). Failover is automatic: 5xx / network errors mark an origin unhealthy for 30 seconds, then it's retried. 

// Configure origins (trailing slash auto-added).
TDCDN.addOrigin('https://cdn.primary.com/v1',   { weight: 10, label: 'primary'   });
TDCDN.addOrigin('https://cdn.secondary.com/v1', { weight: 5,  label: 'secondary' });
TDCDN.addOrigin('/assets',                       { weight: 1,  label: 'local'     });

// Resolve a logical path against the origin list.
const url = await TDCDN.resolve('sprites/ship.png');
// → 'https://cdn.primary.com/v1/sprites/ship.png'

// Or fetch directly (resolve + fetch in one call).
const bytes = await TDCDN.fetchBytes('sprites/ship.png');
const cfg   = await TDCDN.fetchJson('config.json');

Game Kit — TDRest (REST helper)

Wraps fetch() with timeout, retry, default headers (for auth tokens), JSON encoding, and per-host rate-limit tracking (honoring Retry-After). Use it for any HTTP API call your game makes — the docs/PUBLIC_APIS.md survey lists 25+ free, CORS-enabled APIs that work directly from the browser. 

// Configure defaults.
TDRest.setDefaultHeader('Authorization', 'Bearer my-token');
TDRest.setDefaultTimeout(10_000);
TDRest.setDefaultRetries(3);

// Convenience methods (parsed JSON).
const data    = await TDRest.getJson('https://api.example.com/v1/items');
const created = await TDRest.postJson(url, { name: 'Sword', price: 100 });
const updated = await TDRest.putJson(url, body);
await TDRest.del(url);

// Rate-limit aware: 429 with Retry-After is tracked per-host.
try {
  await TDRest.getJson(url);
} catch (e) {
  if (e.rateLimited) showUserMessage('Rate-limited. Try again in ' + Math.ceil(e.retryAfterMs / 1000) + 's');
}

Game Kit — TDServer (server hooks)

Sits on top of TDNet.Socket (the WebSocket transport) and adds the higher-level communication patterns real games need. Pair with the standalone server (see §Standalone server below) for a full client-server stack. 

// Connect to your self-hosted server.
const playerId = await TDServer.connect('wss://your.server/td', {
  authToken: sessionToken,
  roomId:    'arena-1',
});

// Channels (pub/sub per topic, routed per room).
const unsub = TDServer.subscribe('explosions', ({ payload, from }) => {
  spawnExplosion(payload.x, payload.y, from);
});
TDServer.publish('explosions', { x: 100, y: 200 });
await unsub();  // stop listening

// RPC with timeout.
const leaderboard = await TDServer.callRemote('getLeaderboard',
                                              { game: 'pong' },
                                              { timeoutMs: 5000 });

// Presence (who's online in this room).
const peers = TDServer.peers();
TDServer.peerCount();

// Save sync (cross-device roaming via the server).
await TDServer.pushSave('checkpoint-1');
await TDServer.pullSave('checkpoint-1');
const saves = await TDServer.listSaves();

// Register a hook the server can invoke (server → client RPC).
TDServer.registerHook('isReady', () => loaded && playerEntity != null);

Self-hosting

The entire engine is a static .wasm file plus JS glue. Drop the web/ folder on any static host: GitHub Pages, your VPS, a CDN, an intranet, even a USB stick.

To load the engine from a different origin (e.g. your VPN), add ?server=<URL> to the page URL: 

https://your.site/td/?server=https://vpn.example.com/td/

The server_router.js module rewrites all asset URLs (td-engine.wasm, js_bridge.js, style.css, and any other engine asset) to point at the custom server. No recompile, no config file.

Why this matters:   Some schools, offices, and countries block GitHub Pages. The server router lets you mirror the engine on a host your users can actually reach — without forking the code or maintaining a build pipeline.

Standalone self-hosted server (custom game API)

For games that need real multiplayer, save roaming, or authenticated API proxying, the engine ships a complete Node.js server at tools/server/td_server.js. It implements the wire protocol that TDServer (above) speaks, plus everything you need to ship a production game server:

  • WebSocket relay — rooms, presence, channel pub/sub, RPC dispatch, custom client hooks.
  • HTTP asset proxy — protects API keys for Freesound, Unsplash, etc. by keeping the token server-side.
  • File-backed save roaming — players can sign in from any browser and pull their saves.
  • Room management — create / list / join rooms; max-players cap; auto-vacuum when empty.
  • Static file server — serve your game's index.html + assets from one process.
  • Game-defined RPC handlers — register your own methods (e.g. submitScore) in a custom bootstrap script.

The server has one npm dependency: ws (already in the engine's package.json). 

# Quick start
$ npm install                       # installs `ws`
$ mkdir -p public && cp examples/web-game/index.html public/
$ node tools/server/td_server.js \
    --port 8080 \
    --static ./public \
    --saves  ./saves \
    --secrets ./secrets.json

Open http://localhost:8080/ in your browser. The server logs: 

[td_server] listening on http://localhost:8080
[td_server] serving static from: ./public
[td_server] saves stored in: ./saves
[td_server] proxy secrets available for: freesound, unsplash

To register your own RPC handlers (the "custom game API" part), write a small bootstrap script that calls startServer and then server.registerRpc(...): 

// server-bootstrap.js
const { startServer } = require('./tools/server/td_server.js');
const { server } = startServer({ port: 8080, savesDir: './saves' });

// Game-defined RPC handler.
server.registerRpc('submitScore', (args, ctx) => {
  const [score, level] = args;
  console.log(`Player ${ctx.peerId} scored ${score}`);
  return { ok: true, rank: 42 };
});

Then run node server-bootstrap.js instead of td_server.js directly. See docs/SELF_HOSTED_SERVER.md for the full reference (config file format, wire protocol, production deployment, Docker, etc.).

Multiplayer

Two ways to do multiplayer, depending on whether your players are on the same browser or across the internet:

Same-browser (P2P via BroadcastChannel)

Use TDNet.Peer. Open the page in 2+ tabs — each tab is a player. The browser handles the transport via BroadcastChannel, so there's no server to run. Latency is sub-millisecond.

This is the same transport the engine's networking tests use. Open a page that calls TDNet.Peer.join('arena-1') in 2+ tabs and they'll discover each other.

Internet (WebSocket server)

Use TDNet.Socket. You need a WebSocket server that speaks the engine's wire format (JSON envelopes with {kind, from, to, payload}). A 50-line Node.js server is enough. 

// server.js — minimal TD engine WebSocket relay
const WebSocket = require('ws');
const wss = new WebSocket.Server({ port: 8080 });
const clients = new Set();

wss.on('connection', ws => {
  clients.add(ws);
  ws.on('message', msg => {
    // Broadcast to every other client
    for (const c of clients) {
      if (c !== ws && c.readyState === WebSocket.OPEN) c.send(msg);
    }
  });
  ws.on('close', () => clients.delete(ws));
});

Then in the browser: TDNet.Socket.connect('wss://your.server:8080'). Same API as TDNet.Peer — send, sendTo, onMessage, rpc.

Deprecated API tracker

When you change an API, mark the old one deprecated instead of removing it. The tracker will surface a one-time warning in the on-page console (with a purple "Deprecated" filter tab) the first time each deprecated function is called. 

// In your game code (before you remove an old function):
TDDeprecated.warn('oldSpawnFunction', 'v1.2', 'use TDEngine.ecs.create() instead');

Error boundary

WASM crashes used to show "TD Engine failed to load" with no stack. The error boundary now catches window.onerror + unhandledrejection and shows a friendly crash card with the stack trace, metadata (browser, engine version), and Submit/Reload/Dismiss buttons. Reports are saved to localStorage (last 10). 

// Programmatic API (for testing or custom error reporting):
TDErrorBoundary.report(err, { context: 'scene-load' });

// Install with a custom endpoint to receive error reports:
window.__TD_ERROR_ENDPOINT__ = 'https://your.server/errors';
TDErrorBoundary.install({ submitEndpoint: window.__TD_ERROR_ENDPOINT__ });

EXE bundler (Inno Setup-style installer)

The EXE bundler takes a finished web game (your index.html + JS + assets + the engine WASM runtime) and produces a real Windows installer .exe using Inno Setup. This is how you sell your game on Steam / itch.io outside the browser.

Not a self-extracting zip.   The output is a real Inno Setup installer with a wizard UI, per-machine / per-user install scope, Start Menu + Desktop shortcuts, registry entries, file associations (.tdsave, .tdscene), custom install/uninstall hooks, optional save-data cleanup on uninstall, and LZMA2 ultra compression (installers are typically 60-70% smaller than the raw files).

Architecture

┌─ Your game folder ──────────────────────┐
│  index.html + game.js + assets/         │
└──────────────┬──────────────────────────┘
               │
               ▼
┌─ tools/bundler/bundle.py ───────────────────────────┐
│  1. Validate game folder (needs index.html)         │
│  2. Stage: host/ + runtime/ + game/ (+ webview2/)   │
│  3. Substitute placeholders in the .iss template    │
│  4. Invoke ISCC.exe                                  │
│  5. Output: MyGame-Setup.exe                         │
└─────────────────────────────────────────────────────┘

The host shell (src/host/) is a ~300-line C++ program that creates a Win32 window, embeds Microsoft Edge WebView2, and serves your game's game/ folder over a virtual HTTPS host (https://td-game.local/). The virtual host mapping is the key trick: it makes fetch() work for the WASM file (which file:// URLs block for security reasons).

Quick start

# 1. Install Inno Setup 6+ (Windows-only, free)
#    https://jrsoftware.org/isdl.php

# 2. Build the host shell + web runtime
$ cmake -B build -S . -DTD_BUILD_HOST=ON
$ cmake --build build --target td-host
$ make web

# 3. Bundle your game
$ python tools/bundler/bundle.py \
    --game my-game \
    --name "My Cool Game" \
    --version 1.0.0 \
    --publisher "Some Studio" \
    --icon my-game/assets/icon.ico \
    --out MyCoolGame-Setup.exe

# 4. Double-click MyCoolGame-Setup.exe to install

Installed layout

C:\Program Files\My Cool Game\
├── MyCoolGame.exe              ← WebView2 host shell
├── runtime\
│   ├── td-engine.js            ← Emscripten glue
│   ├── td-engine.wasm          ← compiled C++ engine
│   ├── js_bridge.js            ← TDBridge global
│   └── *.js                    ← other web/ modules
├── game\
│   ├── index.html              ← your game's entry point
│   ├── game.js
│   └── assets\
└── unins000.exe                ← Inno Setup uninstaller

Per-user save data lives in %APPDATA%\Some Studio\My Cool Game\saves\ — this is NOT touched during install or update, only optionally during uninstall (with a user prompt, never silent).

Custom install/uninstall steps

Two ways to add custom logic:

  1. Custom .iss — drop an installer.iss in your game folder. bundle.py will use it instead of the default template. Copy installer/td-game-template.iss and modify.
  2. Host hooks — implement --post-install and --pre-uninstall in src/host/webview_host.cpp. The installer probes the registry to check if your host supports these hooks before calling them.

See tools/bundler/README.md for the full CLI reference, production WebView2 SDK setup, CI integration guide, and troubleshooting.
